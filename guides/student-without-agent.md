# AI 없이 시작하기 · 내 결과물에서 미팅 준비까지

AI 구독·명령어·개발 환경 없이 GitHub 웹과 이 체크리스트로 참여할 수 있습니다.
Agent를 쓰는 학생과 같은 준비 기준을 사용합니다. Wiki 편집과 대시보드 정리는 공용 시스템이 맡습니다.
체크리스트가 첫 튜토리얼이고, 이후에는 미팅 준비 Quest로 재사용합니다.

## Quest 1 · 내 공간과 다음 일을 찾기

- [ ] 내 GitHub 계정으로 로그인했고 nii-lab 초대를 수락했다.
- [ ] 담당자에게 배정받은 개인 저장소와 참여 프로젝트를 찾았다.
- [ ] 프로젝트 current에서 목적·최근 결과·내 다음 행동을 확인했다.

아직 초대/배정이 없으면 [참여 접수](participation.md)를 이용합니다. 그동안 로컬 폴더에
실제 작업 결과를 보존할 수 있습니다. 포털 접근이 첫 기록의 선행 조건은 아닙니다.
로그인/내 과업 찾기에서 막히면 [화면별 안내](login-and-next-task.md)를 따릅니다.
진행 중인 요청이 없거나 종료된 프로젝트라면 새 과업을 임의로 만들지 말고 담당자에게 물어봅니다.

## Quest 2 · 실제 결과물 하나 남기기

- [ ] 실제 작업에서 생긴 코드·표·그림·독해 메모·실패 기록 중 하나를 내 저장소에 올렸다.
- [ ] 왜 했는지, 무엇을 확인했는지, 아직 모르는 것과 다음 시작점을 필요한 만큼 덧붙였다.
- [ ] 사용한 설정/입력과 원본 파일을 다시 찾을 수 있다.

저장소에서 **Add file → Upload files**로 업로드하고 변경 내용을 확인해 commit합니다.
짧은 설명은 기존 current.md를 편집하거나 결과물 곁의 README에 남깁니다.
개인 정본의 매 기록에 PR을 만들 필요는 없으며 공동 코드 변경은 저장소의 PR 규칙을 따릅니다.
대용량 파일은 기존 승인 저장소에 보존하고 링크/버전/접근 조건을 남깁니다.
다른 연구실 멤버가 읽을 수 있는 저장소에는 혼자만 볼 메모·비밀번호·개인 정책을 올리지 않습니다.

GitHub 파일에서 `y` 키를 누르면 현재 파일의 고정 버전 링크를 얻을 수 있습니다.
[파일 업로드 공식 안내](https://docs.github.com/en/repositories/working-with-files/managing-files/adding-a-file-to-a-repository) ·
[고정 링크 공식 안내](https://docs.github.com/en/repositories/working-with-files/using-files/getting-permanent-links-to-files)

## Quest 3 · 공용 시스템에 한 번 연결하기

파일 업로드만으로 Wiki가 갱신되지는 않습니다. 현재 집계는 **등록된 허브의 공유 Issue**를 읽습니다.
등록 때 받은 허브 repository와 project_id를 사용합니다. 공개 niil-docs의 Issues는 비공개 연구 제출함이 아닙니다.

- [ ] 연구실 공유가 가능한 내용인지 확인했다.
- [ ] 아래 공유 틀에 내 계정·프로젝트·결과 요약·원본 고정 링크를 넣었다.
- [ ] 등록된 허브에서 본인 계정으로 Issue를 만들고 다시 열어 내용을 확인했다.

아래는 허브 Issue 본문에 넣는 형식입니다. `<...>`를 실제 값으로 바꾸고 JSON의 따옴표/쉼표는 유지합니다.
문장은 한 줄에 쓰고 문장 속 큰따옴표는 피하면 쉽습니다. source.revision은 원본 파일 URL의
`/blob/` 다음 40자리 commit입니다. **실제 GitHub에 존재하는 본인 원본**을 연결합니다.

````text
```niil-record
{
  "schema_version": 1,
  "id": "<내계정-고유한기록이름>",
  "owner_id": "<실제-GitHub-login>",
  "project_id": "<등록된-project_id>",
  "visibility": "lab",
  "status": "accepted",
  "version": 1,
  "title": "<이번에 알아낸 점 또는 남은 질문>",
  "summary": "<결과와 의미를 짧게>",
  "body": "<수행·관찰·한계·근거와 현재 상태>",
  "next_action": "<다음 시작점 또는 필요한 논의>",
  "source": {
    "uri": "<GitHub-원본-고정링크>",
    "revision": "<40자리-commit>"
  }
}
```
````

accepted는 공유 확정이며 연구 성공/교수 수용/미팅 준비 확인을 뜻하지 않습니다.
같은 결과를 수정할 때는 같은 id/Issue를 유지하고 version을 하나 올립니다. 원본도 변경했다면
새 고정 링크로 갱신합니다. 위 틀을 쓰기 어려우면 담당자에게 형식 작성을 도와달라고 요청할 수 있습니다.
최종 게시자는 본인 계정이어야 합니다. 일반 댓글만 남기면 자동 집계되지 않는 현재 제약이 있습니다.

## 매주 Quest · 미팅 전에 확인하기

시스템이 만든 요약이 있으면 그것을 확인하고, 없으면 기존 결과/공유 Issue에서 같은 항목을 봅니다.
정리된 발표 자료를 새로 만들기보다 근거와 질문을 준비하는 것이 우선입니다.

- [ ] 지난 미팅에서 내가 맡은 계획과 실제 결과/시도 근거가 연결돼 있다.
- [ ] 새로 알게 된 점과 실패·미진행·막힌 이유를 사실대로 설명할 수 있다.
- [ ] 함께 논의할 질문과 다음 집중점 제안이 있다.
- [ ] 요약의 사실/해석을 직접 확인했고 필요한 정정을 반영했다.

본인 공유 Issue의 해당 주 구간에 `미팅 준비 확인: 날짜 / 확인한 결과·해석 / 남은 질문`을 남깁니다.
공용 요약에도 반영할 확인/정정은 같은 niil-record의 body에 반영하고 version을 올립니다.
예: body 끝에 미팅 준비 확인 날짜와 확인한 범위/남은 질문을 추가하고 version 1을 2로 바꿉니다.
일반 댓글만 남긴 확인은 자동 집계되지 않으므로 집계 완료로 간주하지 않습니다.
준비 여부를 추적하는 기록이며 성공한 연구 결과만 제출하라는 뜻은 아닙니다.
담당 계획/기여가 공동이라면 각자 맡은 부분을 설명합니다. 활동량/commit 수를 채우지 않습니다.
미팅 후에는 실제 결정·미정·담당·다음 점검 기준을 기존 기록에 연결합니다.

## 시스템 반영 확인과 막힘

- [ ] 공유 Issue와 생성 Wiki에서 같은 id/version/source가 반영됐는지 확인했다.
- [ ] 포털에서 관련 요약/근거를 확인했거나 아직 미반영임을 구분했다.

[현재 상태 진입 안내](login-and-next-task.md)의 생성 현황 경로를 사용합니다.
집계가 지연되면 Issue URL/version과 어떤 화면이 오래됐는지만 담당자에게 전달합니다.
같은 내용을 반복 게시하거나 공유 범위를 넓히지 않습니다. 중앙 배포는 유지보수 담당자가 맡습니다.

가벼운 선택 Quest는 결과/설정 연결이나 다음 시작점 남기기처럼 실제 작업에 도움이 되는 습관입니다.
미팅 준비 연속 달성이나 질문이 구체적으로 변한 사례는 성장 업적이 될 수 있습니다.
휴가/미팅 취소는 해당 주를 건너뛰며, 과거 업적은 유지합니다. 협업은 필요할 때 요청하면 됩니다.
