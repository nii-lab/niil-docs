# 읽는 사람이 활용할 수 있는 연구 보고

기본 양식의 질문에 구체적으로 답하면, 처음 쓰는 사람도 핵심이 빠지지 않는 보고를 만들 수 있어야 한다.
목표는 긴 글이나 빈칸 채우기가 아니라 **받는 사람이 현재 상황을 이해하고 다음 행동을 선택하게 하는 것**이다.
“70점의 기본선”을 제공하되 점수·분량·완료 항목 수를 연구 성과로 계산하지 않는다.

## 먼저 독자와 쓰임을 정한다

작성 전에 아래 세 문장을 생각하고, 첫 문장에 필요한 부분을 반영한다.

- 이 글을 누가 어떤 상황에서 읽는가? 지금 알리기만 하면 되는가, 작업을 이어받는가, 결정을 해야 하는가?
- 상대는 이 정보로 무엇을 할 수 있는가? 지금 결정을 할 근거가 부족하면 무엇이 더 필요한가?
- 전체 연구의 어떤 질문·중간목표에 연결되며, 내 결과가 다음 사람의 입력을 어떻게 바꾸는가?

상급자에게는 전체 목표 영향·병목·선택지·권고 이유·결정 범위가 먼저 보이게 한다. 실행 담당자에게는
입출력·조건·완료 기준·제약이 분명해야 한다. 모든 사람에게 같은 전체 로그를 보내지 않는다.
독자의 의도나 합의를 추측하지 않는다. 사실, 해석, 권고, 승인 여부를 구분한다.

## 첫 화면에 결론, 그 아래 근거

첫 화면은 스크롤 없이 현재 판단과 독자의 다음 행동을 읽을 수 있게 짧게 쓴다.
문장 수를 채우지 말고 문단당 한 가지 역할을 준다. 제목은 “주간 보고” 대신 바뀐 판단을 드러낸다.

1. **독자용 요약**: 목표에 무엇이 달라졌는지, 왜 중요한지, 읽은 뒤 무엇을 할지.
2. **현재 판단**: 검토된 사실 / 그 의미 / 아직 모르는 것.
3. **다음 단계**: 담당자·이유·산출물·진행 조건. 필요한 결정이 없다면 “결정 요청 없음”.
4. **근거와 재사용**: 주장별 근거 링크, 적용 조건, 다음 사람이 사용할 산출물.
5. **재현 상세**: 명령·환경·hash·전체 로그는 접힌 상세 또는 원본 링크.

표는 선택지·조건·결과처럼 서로 비교할 항목에 쓴다. 긴 문장, 여러 다른 질문을 한 셀에 몰아넣지 않는다.
상태는 완료/진행 같은 단어만 쓰지 말고 무엇이 검증·대기 중인지 쓴다. 수치는 단위·분모·조건을 붙인다.
상세 링크는 “여기” 대신 그 링크에서 확인할 근거를 이름으로 쓴다. 링크를 열지 않아도 결론을 이해할 수 있어야 한다.

## 복사해서 쓰는 세 가지 양식

- [진행·요청 보고](https://github.com/nii-lab/niil-docs/blob/main/templates/reporting/progress.md): 결과·blocker·판단이 바뀌었을 때. 대부분은 이것 하나로 충분하다.
- [실험 결과](https://github.com/nii-lab/niil-docs/blob/main/templates/reporting/experiment.md): 조건과 유효 범위, 재현·재사용 가능한 산출물이 생겼을 때.
- [세미나 정리](https://github.com/nii-lab/niil-docs/blob/main/templates/reporting/seminar.md): 실제 논의 이후 결정과 후속 과업을 남길 때.
- [피드백과 개선](https://github.com/nii-lab/niil-docs/blob/main/templates/reporting/feedback.md): agent 사전 점검과 Owner의 형성적 피드백.

모든 양식을 매번 제출하지 않는다. 모르는 항목은 “미확인 + 판단 영향 + 확인 방법”으로 적는다.
불필요한 항목은 이유를 짧게 쓰거나 삭제한다. 근거·수치·논의·동의·실행 결과를 만들어 채우지 않는다.
설치·조회·hash 확인·commit 횟수는 연구 성과나 진척률이 아니다. 반복 검증은 입력 변화·유효성 우려와
다음 판단에 주는 가치가 있을 때 한다. 별도 요청된 인수 테스트는 그 목적과 완료 기준을 따른다.
변화와 승인된 유효 작업이 없는 예약 확인은 공개 댓글 없이 로컬 처리 좌표만 남긴다.

## 같은 사실을 더 유용하게 쓰기

부족한 예: “모델 설치와 테스트를 완료했습니다. 다음 실험을 하겠습니다.”

개선 예(가상): “모델 로딩은 확인했지만, 이번 실행에는 장애물이 없어 좁은 환경에서의 작업 가능성은
판단할 수 없습니다. 다음 담당자가 장애물 포함 조건을 재현할 수 있도록 장면 파일과 실행 방법을 연결했습니다.
다음 단계는 동일 목표에서 충돌 판정을 확인하는 것입니다. 현재 상급자 결정 요청은 없습니다.”

실제 보고에는 검증 조건·결과·산출물의 구체적인 근거를 붙인다. 실행 성공을 가설 검증으로 바꾸어 쓰지 않는다.

## 보고에서 연구 전체로 환류

과학적 정본은 프로젝트 current/승인된 계획이다. Issue 본문 상단은 최신 상태로 갱신하고 이전 가이드·긴 로그는
상세에 보존한다. 새 댓글 전체를 읽어야 현재 상황을 알 수 있게 만들지 않는다.
Worker는 결과와 권고를 보고하며 Owner의 수용이나 세미나 합의를 대신 완료하지 않는다.
Owner는 의미 있는 결과를 수용할 때 current·관련 Issue 현재 본문·lab 공유 판단 요약을 함께 맞춘다.
정책 밖 게시/작업은 대기로 표시한다. 문장 점검이 연구 수용이나 권한 승인을 대신하지 않는다.

등록된 프로젝트 Owner는 선택적 niil-record brief v1로 목표·질문·현재 답·의미·미확정·다음 판정·예상 산출물을
공유한다. findings는 reviewed/reported, milestones는 done/current/later, work는 담당 역할·이유·산출물·조건과
agent/human 주의를 담는다. 계약은 연결된 private hub의 ops/live/decision-reporting.md를 따른다.
Agent는 개인 초안 전체를 가져오지 않고, 본인이 lab 공유로 승인한 보고에서만 Wiki·대시보드를 갱신한다.

## 피드백이 누적되는 방법

제출 전 작성자 agent가 피드백 양식의 독자 점검을 수행한다. 해결 가능한 표현·누락은 초안에서 바로 고치고,
근거 부족은 표시한다. 형식 통과를 내용 검증으로 포장하거나 매번 별도 점검 댓글을 만들지 않는다.
Owner는 실제 내용을 검토할 때 강점 하나, 판단을 막는 핵심 문제 하나, 다음 수정 행동을 같은 Issue에 남긴다.
내용이 충분하면 수정 과업을 억지로 만들지 않는다. 과학적 수용과 글쓰기 조언을 구분한다.

작성자는 다음 의미 있는 제출에서 수정 결과를 반영한다. 해석·판단에 영향을 준 오류는 즉시 본문에 정정하고
짧은 정정 이력을 남긴다. 단순 문장 교정은 수정본을 중복 게시하지 않는다.
동일한 읽기 문제를 여러 보고에서 반복 발견하면 기존 프로젝트 회고/세미나에 예시와 함께 모은다.
Owner는 “양식 부족 / 안내 부족 / 내용·근거 부족”을 구분해 한 번에 작은 개선을 PR로 제안한다.
다음 실제 보고에서 독자가 더 적은 왕복으로 판단·재사용할 수 있었는지 확인하고 효과가 없으면 되돌린다.
새 정기 회의·상시 채점·자동 독촉·서비스를 추가하지 않는다. 개인정보와 미공개 연구 예시는 공개 매뉴얼에 옮기지 않는다.

## 축척에 맞게 정보를 전달한다

연구실 전체 → 프로젝트 → 담당 과업 → 개별 보고 → 원본 근거 순서로 상세를 나눈다.
첫 화면의 역할은 전체 위치와 주의할 점을 파악하는 것이다. 보고서 전체를 축소해서 붙이지 않는다.
프로젝트에서는 현재 질문·검토된 답·다음 판정·역할 의존관계를, 과업에서는 다음 산출물과 실제 보고를,
보고서에서는 주장·근거·한계와 재사용 조건을 제공한다. 외부 원본은 새 탭으로 연다.

포털용 짧은 요약은 상태 / 확인된 성과 / 병목 / 다음 조건 / 필요한 결정의 다섯 항목을 각 한 문장으로 쓴다.
별도의 “한눈에” 문단으로 같은 내용을 반복하지 않는다. 짧게 만들며 조건·미확정을 삭제하지 않는다.
원본 검토 기준 revision/시점과 공용 반영 상태를 구분한다. 새 보고를 쓴 시각만으로 연구 판단을 최신으로
표시하지 않으며, agent가 공유했다는 사실을 포털에서 반영 확인한 것으로 바꾸지 않는다.

실제 역할 보고를 적용한 첫 검증에서 중복 요약과 정본→공용 요약의 연결 지연이 드러났다.
앞으로는 의미 있는 Owner 판정이 바뀌면 사용 중인 공용 요약과 비교해 환류하고, 변경이 없는 조회에는
재게시하지 않는다. 독자 검증은 먼저 요약 화면만 보고 질문/현재 답/병목/다음 산출물/필요 결정을 답해 본 뒤
원본과 대조한다. 화면만으로 답할 수 없는 부분은 해당 축척의 표시나 요약을 고친다.
관리 agent의 대조 검증과 실제 사람의 사용성 검증은 구별해서 기록한다.


## 내 과업과 프로젝트의 병목

교수/관리자는 프로젝트 전체의 현재 병목·담당자·풀리는 조건과 필요한 결정을 먼저 본다.
학생은 본인이 수행할 과업·필요한 입력·제출물·받을 피드백을 먼저 보고, 자기 과업에서 프로젝트 미니맵으로 올라간다.
같은 연구 정본을 사용하되 기본 관심 대상과 정보 순서가 다르다. 개인 위임과 사람의 결정권은 화면 역할과 별개다.

보고의 현재 상태는 준비/진행 중/인수 대기/막힘/결과 검토/완료를 구분한다. 예약이 켜져 있다는 사실을
실험 실행 중이라고 쓰지 않는다. 막힘/대기에는 누구의 어떤 입력으로 풀리는지와 해당 과업 링크를 함께 쓴다.
현재 지점에서 직전의 확인된 결과와 다음 인수·판정으로 이어질 수 있어야 한다. 시간 경과만으로 멈춤을 추정하지 않는다.
미니맵·퀘스트는 이 실제 상태를 이해하는 표현이며 새로운 업무, 권한이나 연구 성과를 만들어내지 않는다.
알림은 의미 있는 새 공유 결과·상태·결정에 연결하며 반복 조회를 알리지 않는다.
