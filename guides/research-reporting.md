# 읽는 사람이 활용할 수 있는 연구 보고

기본 양식의 질문에 구체적으로 답하면, 처음 쓰는 사람도 핵심이 빠지지 않는 보고를 만들 수 있어야 한다.
목표는 긴 글이나 빈칸 채우기가 아니라 **받는 사람이 현재 상황을 이해하고 다음 행동을 선택하게 하는 것**이다.
“70점의 기본선”을 제공하되 점수·분량·완료 항목 수를 연구 성과로 계산하지 않는다.

## 먼저 독자와 쓰임을 정한다

작성 전에 아래 세 문장을 생각하고, 첫 문장에 필요한 부분을 반영한다.

- 이 글을 누가 어떤 상황에서 읽는가? 지금 알리기만 하면 되는가, 작업을 이어받는가, 결정을 해야 하는가?
- 상대는 이 정보로 무엇을 할 수 있는가? 지금 결정을 할 근거가 부족하면 무엇이 더 필요한가?
- 전체 연구의 어떤 질문·중간목표에 연결되며, 내 결과가 다음 사람의 입력을 어떻게 바꾸는가?

상급자에게는 전체 목표 영향·병목·선택지·권고 이유·결정 범위가 먼저 보이게 한다. 실행 담당자에게는
입출력·조건·완료 기준·제약이 분명해야 한다. 모든 사람에게 같은 전체 로그를 보내지 않는다.
독자의 의도나 합의를 추측하지 않는다. 사실, 해석, 권고, 승인 여부를 구분한다.

## 첫 화면에 결론, 그 아래 근거

첫 화면은 스크롤 없이 현재 판단과 독자의 다음 행동을 읽을 수 있게 짧게 쓴다.
문장 수를 채우지 말고 문단당 한 가지 역할을 준다. 제목은 “주간 보고” 대신 바뀐 판단을 드러낸다.

1. **독자용 요약**: 목표에 무엇이 달라졌는지, 왜 중요한지, 읽은 뒤 무엇을 할지.
2. **현재 판단**: 검토된 사실 / 그 의미 / 아직 모르는 것.
3. **다음 단계**: 담당자·이유·산출물·진행 조건. 필요한 결정이 없다면 “결정 요청 없음”.
4. **근거와 재사용**: 주장별 근거 링크, 적용 조건, 다음 사람이 사용할 산출물.
5. **재현 상세**: 명령·환경·hash·전체 로그는 접힌 상세 또는 원본 링크.

표는 선택지·조건·결과처럼 서로 비교할 항목에 쓴다. 긴 문장, 여러 다른 질문을 한 셀에 몰아넣지 않는다.
상태는 완료/진행 같은 단어만 쓰지 말고 무엇이 검증·대기 중인지 쓴다. 수치는 단위·분모·조건을 붙인다.
상세 링크는 “여기” 대신 그 링크에서 확인할 근거를 이름으로 쓴다. 링크를 열지 않아도 결론을 이해할 수 있어야 한다.

## 복사해서 쓰는 세 가지 양식

- [진행·요청 보고](https://github.com/nii-lab/niil-docs/blob/main/templates/reporting/progress.md): 결과·blocker·판단이 바뀌었을 때. 대부분은 이것 하나로 충분하다.
- [실험 결과](https://github.com/nii-lab/niil-docs/blob/main/templates/reporting/experiment.md): 조건과 유효 범위, 재현·재사용 가능한 산출물이 생겼을 때.
- [세미나 정리](https://github.com/nii-lab/niil-docs/blob/main/templates/reporting/seminar.md): 실제 논의 이후 결정과 후속 과업을 남길 때.
- [피드백과 개선](https://github.com/nii-lab/niil-docs/blob/main/templates/reporting/feedback.md): agent 사전 점검과 Owner의 형성적 피드백.

모든 양식을 매번 제출하지 않는다. 모르는 항목은 “미확인 + 판단 영향 + 확인 방법”으로 적는다.
불필요한 항목은 이유를 짧게 쓰거나 삭제한다. 근거·수치·논의·동의·실행 결과를 만들어 채우지 않는다.
설치·조회·hash 확인·commit 횟수는 연구 성과나 진척률이 아니다. 반복 검증은 입력 변화·유효성 우려와
다음 판단에 주는 가치가 있을 때 한다. 별도 요청된 인수 테스트는 그 목적과 완료 기준을 따른다.
변화와 승인된 유효 작업이 없는 예약 확인은 공개 댓글 없이 로컬 처리 좌표만 남긴다.

## 같은 사실을 더 유용하게 쓰기

부족한 예: “모델 설치와 테스트를 완료했습니다. 다음 실험을 하겠습니다.”

개선 예(가상): “모델 로딩은 확인했지만, 이번 실행에는 장애물이 없어 좁은 환경에서의 작업 가능성은
판단할 수 없습니다. 다음 담당자가 장애물 포함 조건을 재현할 수 있도록 장면 파일과 실행 방법을 연결했습니다.
다음 단계는 동일 목표에서 충돌 판정을 확인하는 것입니다. 현재 상급자 결정 요청은 없습니다.”

실제 보고에는 검증 조건·결과·산출물의 구체적인 근거를 붙인다. 실행 성공을 가설 검증으로 바꾸어 쓰지 않는다.

## 보고에서 연구 전체로 환류

과학적 정본은 프로젝트 current/승인된 계획이다. Issue 본문 상단은 최신 상태로 갱신하고 이전 가이드·긴 로그는
상세에 보존한다. 새 댓글 전체를 읽어야 현재 상황을 알 수 있게 만들지 않는다.
Worker는 결과와 권고를 보고하며 Owner의 수용이나 세미나 합의를 대신 완료하지 않는다.
Owner는 의미 있는 결과를 수용할 때 current·관련 Issue 현재 본문·lab 공유 판단 요약을 함께 맞춘다.
정책 밖 게시/작업은 대기로 표시한다. 문장 점검이 연구 수용이나 권한 승인을 대신하지 않는다.

등록된 프로젝트 Owner는 선택적 niil-record brief v1로 목표·질문·현재 답·의미·미확정·다음 판정·예상 산출물을
공유한다. findings는 reviewed/reported, milestones는 done/current/later, work는 담당 역할·이유·산출물·조건과
agent/human 주의를 담는다. 계약은 연결된 private hub의 ops/live/decision-reporting.md를 따른다.
Agent는 개인 초안 전체를 가져오지 않고, 본인이 lab 공유로 승인한 보고에서만 Wiki·대시보드를 갱신한다.

## 피드백이 누적되는 방법

제출 전 작성자 agent가 피드백 양식의 독자 점검을 수행한다. 해결 가능한 표현·누락은 초안에서 바로 고치고,
근거 부족은 표시한다. 형식 통과를 내용 검증으로 포장하거나 매번 별도 점검 댓글을 만들지 않는다.
Owner는 실제 내용을 검토할 때 강점 하나, 판단을 막는 핵심 문제 하나, 다음 수정 행동을 같은 Issue에 남긴다.
내용이 충분하면 수정 과업을 억지로 만들지 않는다. 과학적 수용과 글쓰기 조언을 구분한다.

작성자는 다음 의미 있는 제출에서 수정 결과를 반영한다. 해석·판단에 영향을 준 오류는 즉시 본문에 정정하고
짧은 정정 이력을 남긴다. 단순 문장 교정은 수정본을 중복 게시하지 않는다.
동일한 읽기 문제를 여러 보고에서 반복 발견하면 기존 프로젝트 회고/세미나에 예시와 함께 모은다.
Owner는 “양식 부족 / 안내 부족 / 내용·근거 부족”을 구분해 한 번에 작은 개선을 PR로 제안한다.
다음 실제 보고에서 독자가 더 적은 왕복으로 판단·재사용할 수 있었는지 확인하고 효과가 없으면 되돌린다.
새 정기 회의·상시 채점·자동 독촉·서비스를 추가하지 않는다. 개인정보와 미공개 연구 예시는 공개 매뉴얼에 옮기지 않는다.

## 축척에 맞게 정보를 전달한다

연구실 전체 → 프로젝트 → 담당 과업 → 개별 보고 → 원본 근거 순서로 상세를 나눈다.
첫 화면의 역할은 전체 위치와 주의할 점을 파악하는 것이다. 보고서 전체를 축소해서 붙이지 않는다.
프로젝트에서는 현재 질문·검토된 답·다음 판정·역할 의존관계를, 과업에서는 다음 산출물과 실제 보고를,
보고서에서는 주장·근거·한계와 재사용 조건을 제공한다. 외부 원본은 새 탭으로 연다.

포털용 짧은 요약은 상태 / 확인된 성과 / 병목 / 다음 조건 / 필요한 결정의 다섯 항목을 각 한 문장으로 쓴다.
별도의 “한눈에” 문단으로 같은 내용을 반복하지 않는다. 짧게 만들며 조건·미확정을 삭제하지 않는다.
원본 검토 기준 revision/시점과 공용 반영 상태를 구분한다. 새 보고를 쓴 시각만으로 연구 판단을 최신으로
표시하지 않으며, agent가 공유했다는 사실을 포털에서 반영 확인한 것으로 바꾸지 않는다.

실제 역할 보고를 적용한 첫 검증에서 중복 요약과 정본→공용 요약의 연결 지연이 드러났다.
앞으로는 의미 있는 Owner 판정이 바뀌면 사용 중인 공용 요약과 비교해 환류하고, 변경이 없는 조회에는
재게시하지 않는다. 독자 검증은 요약에서 전체 방향·현재 위치·다음 담당을 파악한 뒤, 모르는 지점만 선택·펼치기로
따라가 질문이 해결되는지 확인하고 원본과 대조한다. 모든 설명을 첫 화면에 넣지 않는다.
필요한 설명이 없거나 같은 요약만 반복되는 깊이는 해당 표시와 내용을 함께 고친다.
관리 agent의 대조 검증과 실제 사람의 사용성 검증은 구별해서 기록한다.


## 내 과업과 프로젝트의 병목

교수/관리자는 프로젝트 전체의 현재 병목·담당자·풀리는 조건과 필요한 결정을 먼저 본다.
학생은 본인이 수행할 과업·필요한 입력·제출물·받을 피드백을 먼저 보고, 자기 과업에서 프로젝트 미니맵으로 올라간다.
같은 연구 정본을 사용하되 기본 관심 대상과 정보 순서가 다르다. 개인 위임과 사람의 결정권은 화면 역할과 별개다.

보고의 현재 상태는 준비/진행 중/인수 대기/막힘/결과 검토/완료를 구분한다. 예약이 켜져 있다는 사실을
실험 실행 중이라고 쓰지 않는다. 막힘/대기에는 누구의 어떤 입력으로 풀리는지와 해당 과업 링크를 함께 쓴다.
현재 지점에서 직전의 확인된 결과와 다음 인수·판정으로 이어질 수 있어야 한다. 시간 경과만으로 멈춤을 추정하지 않는다.
미니맵·퀘스트는 이 실제 상태를 이해하는 표현이며 새로운 업무, 권한이나 연구 성과를 만들어내지 않는다.
알림은 의미 있는 새 공유 결과·상태·결정에 연결하며 반복 조회를 알리지 않는다.


## Flow graph에서 보고를 읽고 넘기기

`request → intake → execution → result → review`는 실제 입력/산출물과 근거가 있는 전환이다.
Actor lane은 누가 처리하는지, node state는 실제 진행/대기/완료, edge는 누구에게 무엇을 전달하는지 보여준다.
`Pending`/`Planned`와 조건부 `rework`를 이미 요청/실행/실패한 사건으로 쓰지 않는다.
변화가 생기면 source/revision·보낸 입력·받은 산출물·판정·다음 transition condition을 기존 보고에 연결한다.
노드를 고르면 같은 화면의 Output/Evidence/Transition을 읽고, 작성·응답·원본 검산이 필요할 때 해당 원문으로 간다.

보고나 화면의 각 요소는 다음 질문으로 검토한다: 꼭 필요한가, 왜 필요한가, 역할에 가장 효율적인 표현은 무엇인가,
읽은 사람이 바로 다음에 필요로 하는 것은 무엇인가. Map은 짧은 technical term/state/관계로, 상세는 구체 입력·결과·한계로 쓴다.
Technical term은 English 원문을 유지하고 필요한 의미만 자연스러운 설명으로 잇는다. 긴 문장·링크 수·완료 개수 자체는 성과가 아니다.

## 아는 사람은 빠르게, 모르는 지점은 더 깊게

주 독자는 연구 참여자다. 첫 화면을 초보자용 설명서로 바꾸지 않는다. 익숙한 이름·technical term은
유지하되 무엇을 한 단계인지 식별할 짧은 설명을 곁들인다. English term을 유지한다는 지침은 문장
전체를 영어로 쓰라는 뜻이 아니다. 문장은 자연스러운 한국어로 쓰며 정확한 개념명만 원문을 쓴다.

Map은 전체 관계·현재 위치·다음 담당을, 선택한 단계는 실제로 한 일·얻은 답·후속 과업의 이유를
보여준다. 그다음 펼치기에는 이름의 뜻·배경·입력·방법·비교 조건을, 근거 단계에는 검산·한계와
재현 원본을 둔다. 전체에서 상세까지 매번 같은 문단을 반복하거나 긴 설명을 잘라 여러 클릭에
나누지 않는다. 원본 링크는 해당 설명을 대신하지 않으며, 열면 무엇을 확인할 수 있는지 알 수 있어야 한다.

작성자는 각 깊이에서 독자가 품을 질문을 적어보고 바로 다음 깊이가 그 질문에 답하는지 확인한다.
익숙한 독자가 필요 없는 설명을 건너뛸 수 있는지, 낯선 독자가 선택적으로 읽어 이해할 수 있는지를
함께 시험한다. 테스트는 첫 화면에서 모든 것을 맞히는 시험이 아니다. “모른다 → 더 읽는다 →
이해하거나 다음 행동을 정한다”가 이어지는지 확인한다. 결과 수치에는 비교 대상·단위·분모·판정
의미를 붙인다. 세부 방법과 무관한 독자도 핵심 결과를 읽을 수 있도록 필요하면 작은 비교 그림을 쓴다.

## 독자의 질문에 맞춰 표현을 고른다

문장·수식·표·그래프·도식·이미지·영상 중 무엇이 이해나 판단의 수고를 가장 줄이는지 고른다.
그림 수를 채우거나 모든 보고에 같은 종류를 강요하지 않는다. 짧은 문장이 더 명확하면 그대로 쓴다.
핵심 질문 하나에 가장 효율적인 표현을 먼저 고르고, 다른 질문을 풀어줄 때만 두 번째 자료를 더한다.

| 독자가 풀어야 할 질문 | 우선 검토할 표현 | 선택할 때 확인할 점 |
| --- | --- | --- |
| 무엇이 어디에 놓이고 어떤 구성을 비교하나? | 배치도·단면도·개념도, 주석을 붙인 실제 장면 이미지 | 같은 시점·척도로 비교. 개념도를 실제 시뮬레이션 결과처럼 보이지 않게 표시한다. |
| 정확한 조건·값·예외를 찾아야 하나? | 표 | 단위·분모·조건을 행/열에 두고 필요한 셀을 찾기 쉽게 한다. |
| 조건에 따라 얼마나 달라지나? | bar/dot chart | 범주별 차이를 비교한다. 기준·분모·같은 축과 정확한 수치에 접근할 경로를 보존한다. |
| 시간·입력 크기에 따라 어떻게 변하나? | line plot·scatter plot | 선으로 이어도 되는 순서/연속성인지, 상관과 인과를 혼동하지 않는지 확인한다. |
| 변동·불확실성·분포는 어떤가? | 개별점·histogram·box plot·interval | 표본 수와 interval 정의를 밝힌다. 반복이 없는데 오차막대를 만들지 않는다. |
| 위치별 성능·실패가 어디에 몰리나? | spatial map·heatmap·주석 이미지 | 좌표·색 범례·미측정 영역을 표시한다. 색의 강도를 성공 확률로 오해하지 않게 한다. |
| 누가 무엇을 주고받고 어느 조건에서 다음으로 가나? | flow/state/sequence diagram | 실제 전달·예정·조건부 분기를 구분하고 입력·판정·담당을 연결한다. |
| 어떤 양이 어떤 관계로 결정되나? | 수식·정의·짧은 계산 예 | 변수·단위·가정·유효 범위를 바로 곁에 둔다. 수식이 명확한 경우 억지로 그림으로 바꾸지 않는다. |
| 방법을 어떻게 실행하거나 구현하나? | pseudocode·단계도·작은 입출력 예 | 실제 순서/분기와 필요한 입력을 드러낸다. 긴 코드 전체를 본문에 넣지 않는다. |
| 성공·실패가 구체적으로 어떻게 보이나? | 전후 이미지·대표/실패 사례·짧은 영상 | 고른 이유와 전체 결과에서의 위치를 밝힌다. 좋은 예 하나를 전체 성능의 증거로 쓰지 않는다. |
| 시간에 따른 움직임이 핵심인가? | 짧은 영상·key frame sequence + 정량 결과 | 캡처/조건/재생 속도를 밝힌다. 정지 화면만으로 연속 경로·접촉 안정성을 입증하지 않는다. |

**배치:** 비교 구성을 설명하는 도식은 그 구성을 설명하는 문장 곁에, 결과 그림은 그 결과를 주장하는
문장 곁에 둔다. 전체 flow map에는 방향·관계만 남기고 구체 그림은 해당 단계 선택 후 보여준다.
크게 보기·수식 유도·추가 사례·원본 영상은 더 깊은 단계에 둔다. 핵심을 이해하려고 먼저 외부 링크를
열어야 하게 만들지 않는다. 본문과 그림을 서로 참조하게 하되 같은 설명 전체를 반복하지 않는다.

**사용할 때의 기본 조건:** 제목/캡션은 이 자료로 무엇을 읽을지 말한다. 관측·계산 결과와 개념도·
예시·예측을 명시적으로 구분한다. 데이터/장면/모델 출처와 revision을 찾을 수 있게 하고, 의미에
영향을 주는 단위·축·분모·범례·비교 조건·불확실성을 생략하지 않는다. 수식은 변수/가정, 영상은
조건/시간 정보를 붙인다. 색만으로 의미를 구분하지 않으며 대체 설명을 제공한다. AI 생성 이미지를
관측 증거나 실제 장면으로 제시하지 않는다. 기밀·공유 범위는 원자료와 동일하게 지킨다.

**독자 점검:** “이 표현이 없으면 어디에서 막히나?”, “보고 바로 어떤 차이/관계/행동을 알게 되나?”,
“더 간단한 표현이 있나?”를 묻는다. 그림을 봐도 질문이 남으면 그림과 설명을 함께 고친다.
불필요한 장식·같은 정보를 반복한 차트·목적 없는 이미지 링크는 줄인다.

**경험을 필수 항목으로 바꾸기:** 기존 보고 피드백/세미나에 `막힌 질문 → 선택한 표현 → 이해·판단의
변화`를 짧게 남긴다. 비슷한 보고에서 효과가 반복 확인되면 해당 보고 유형과 상황에 한정해
양식의 필수 요소로 올린다. 적용 이유·근거 예시·적용 범위·대체 가능한 동등 표현을 함께 적고 다음
실제 보고에서 효용을 재확인한다. 필요가 없어지면 완화한다. 별도 회의·승인·채점 체계는 만들지
않는다. 현재는 특정 그림 종류/개수의 일괄 의무화보다 질문에 맞는 선택을 권장한다.

그림을 다음 agent와 공용 화면에 넘길 때는 생성 source/revision·재현 방법·그림 파일 hash와 함께
제목·alt·판단용 caption·계산/관측/개념 분류·공유 허용 범위를 전달한다. 큰 원본은 producing host에
보존하고, 공용 화면에는 명시적으로 공유한 작은 파생 그림만 사용한다. NiiL 멤버 포털의 대표 PNG는
해당 과업을 선택했을 때 보이며, 추가 그림·원본 크기·방법은 필요한 경우 선택한다. Wiki는 같은
캡션·출처와 해석 범위를 이어받는다. 그림 전달/수용과 실제 포털 반영은 구분해 확인한다.

## 자율적인 소통과 정직한 편집

기존 프로젝트 공유 범위와 본인에게 위임된 게시 권한 안에서 Issue/댓글의 문안·시점은 작성자가
정한다. 관리자의 사전 문안 승인이나 상급자의 취향을 맞히는 절차를 두지 않는다. 미완성 관찰·
질문·반론도 그 상태와 근거를 밝혀 공유할 수 있다. 양식과 독자 점검은 정보의 질을 높이는
도움말이며 완벽하게 채우기 전까지 발언을 보류시키는 통과 시험이 아니다.

상대의 시간을 아껴주고 큰 그림을 쉽게 파악하게 하는 배려는, 상대가 좋아할 결론을 예상해서
보고 내용을 고르는 일이 아니다. 사실·해석·권고를 구분하고 불리한 결과·실패·반례·불확실성·
다른 의견도 현재 판단에 중요한 만큼 드러낸다. 관리자나 Owner의 가정도 근거가 반박하면
명확히 지적한다. 요약·그림의 축·view·대표 사례를 고를 때 좋은 인상을 만들기 위한 선택이
결론을 바꾸지 않는지 확인한다. 압축한 정보의 원본과 중요한 한계에 접근할 수 있게 한다.

동료·Owner·관리자는 게시된 내용을 읽고 오류를 적극적으로 지적한다. 작성자는 이유·영향·
다음 조치를 후속 댓글이나 필요한 새 Issue에 연결하고 본문의 최신 요약·current·공유 해석을
맞춘다. 과학적 수용과 다음 실행 범위는 해당 책임자의 판단이며, 다른 사람의 의견 게시를
허락하는 권한과 구분한다. 일반적인 실패·이견을 상급자 눈치를 보며 숨기지 않는다.

## 흐름 사이를 잇는 세 문장

각 흐름의 첫 설명은 “앞에서 무엇을 얻었나 → 어떤 의문이 남았나 → 왜 이번 질문을 선택했나”로 연결한다. 첫 시작은 최초 입력/목적을 쓴다. 흐름 목록의 앞뒤 순서와 실제 의존관계는 별개다. 직접 입력 인계, 질문·범위 전환, 병렬 분기, 마감 후 재개를 구분하고 관계를 뒷받침하는 원문·revision을 연결한다.

사후 해설은 작성자·기준시점·근거를 표시한다. “당시 대기”와 이후 수용/마감이 동시에 보이면 후속 근거와 전후 시점을 명시한다. 당시 실패·이견을 삭제해 현재로 덮지 않는다. 같은 변수명·후보·허용오차가 다른 계약이면 차이를 설명하고 한 결과를 다른 조건에 복사하지 않는다. 선택값은 최적·실물 기준인지, 작은 진단을 위해 고정한 변수인지 구분한다.

첫 설명은 시작 이유·얻은 결과·다음 질문/종료 이유까지만 보이게 한다. 정확 입력/산출물·관계·용어는 필요할 때 펼치고, 원문에서는 재현/검산 상세를 찾게 한다. 종료 보고의 핵심 결론·종료 범위는 접힘 밖에 둔다.

## 작업의 경계 · 입력에서 다음 인수까지

단계 이름만으로 전달을 끝내지 않는다. 각 단계의 상세에는 아래 다섯 줄을 채운다.

| 항목 | 적을 내용 |
|---|---|
| 받은 입력 | 앞 단계/작성자, 실제 산출물의 정확 URL·revision, 전달 완료/대기. 시작 단계라면 최초 입력의 출처 |
| 착수 정의 | 그 입력으로 풀 질문과 첫 행동. 필요한 입력·권한·환경이 갖춰졌는지, 부족하면 누구의 무엇으로 풀리는지 |
| 수행·종료 기준 | 이번 단계가 남길 결과와 검토 기준·예산·중단 조건. 실행 완료와 결과 수용을 구분 |
| 넘길 산출물 | 다음 사람이 실제로 사용할 파일/결과/판단·실패·한계. 예정과 실제 제출을 구분 |
| 다음 인수 | 받는 사람·단계, 전달할 내용, 수신자가 무엇을 판단/시작할지. 후속이 없다면 그 범위를 명시 |

Map의 번호는 읽기 안내다. 번호가 연속이어도 연결선이 없으면 순차 실행 의존관계로 해석하지 않는다.
담당자 lane을 건너는 전달과 재검토로 되돌아가는 연결을 표시한다. 기존 입력을 참조할 때 전체 내용을 복제하지 않고 정확한 원본으로 연결한다.
착수 조건이나 인수자가 없으면 미등록으로 남기고, 보기 좋은 흐름을 만들기 위해 임의로 채우지 않는다.

## 종료 보고 · 작업 묶음과 프로젝트 전체를 구분

처음에 목표·포함/제외 범위·예상 산출물·완료 판정을 기록한다. 종료할 때 같은 기준과 대조한다.
‘모든 node가 done’, ‘새 Issue 없음’, ‘예약이 idle’만으로 프로젝트 전체 종료를 선언하지 않는다.
Owner가 한정 작업 묶음/프로젝트 전체 중 무엇을 종료하는지와 그 근거를 남긴다. **연구 판단 종료와 자료·공용 마감 완료를 별도로 표시한다.** 정리가 남았다면 담당·산출물·완료 조건이 있는 정리 과업으로 남기며, 종료한 연구를 다시 실행해 메우지 않는다. 다음 사람이 첫 화면에서 읽을 종료 보고는 다음 순서로 정리한다.

1. **요약·결론:** 무엇을 물었고 무엇을 알았나? 채택/불채택·보류한 것과 근거, 이번 결론의 범위.
2. **목표 대비 결과:** 원래 완료 기준별 실제 근거·미달·변경 이유. 실패와 반례도 결과다.
3. **대표 결과물:** 재사용할 문서·코드/source revision·입력·결과·필수 그림의 짧은 목록. 각 항목은 무엇에 쓰고 어디서 시작하는지 표시한다. 단순 링크 모음으로 끝내지 않는다.
4. **최적화·정돈:** 중복된 현재 요약을 하나의 정본으로 통합하고 stale 대기/다음 행동을 정정한다. 현재 navigation은 핵심만, 예전 실행·논의·실패는 이력으로 둔다. 원본/반례/라이선스·재현 입력은 삭제하지 않는다. 실제 정돈한 항목과 미정돈 항목을 구분한다.
5. **남은 한계·후속:** 미검증·해결하지 않은 질문과 운영 유지보수를 구분한다. 다음 목표가 정해졌으면 담당·필수 입력·첫 행동·완료 기준을, 없으면 새 실행 없음/후속 선택 조건을 명시한다.
6. **환류 확인:** 정본 current·Issue 현재 머리말·공유 Wiki·대시보드가 같은 결론을 가리키는지 확인한다. 배포/API 성공과 실제 화면 확인은 구분한다.

이 정돈은 보고의 품질 관리이며 사전 검열이 아니다. 나쁜 결과나 이견을 지우거나 상급자가 선호할 결론으로 바꾸지 않는다.
종료 보고는 기존 수용·위임 규칙 안에서 처리하며 새로운 상시 승인 절차를 추가하지 않는다.

새로 생성한 개인·공동 공간에는 reporting/ 사본이 함께 있다. 이미 사용 중인 공간은 원본 templates/reporting/에서 필요한 양식만 가져오며 current·개인 위임을 초기화하지 않는다. 양식을 모두 쓰거나 같은 문장을 여러 파일에 반복하지 않는다. Agent는 재개 시 current의 상태/범위를 먼저 읽고, 범위가 종료됐다면 closeout과 남은 실제 정리만 확인한다.
