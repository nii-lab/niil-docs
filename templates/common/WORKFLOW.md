# NiiL 학생·Agent 업무 흐름 · 1.0

AGENTS.md의 공통 계약에 연결된 수행 가이드다. Codex/Claude Code 모두 같은 문서를 읽는다.
계정·권한·자동 실행은 개인 정책과 실제 프로젝트 설정을 따르며 이 가이드가 확대하지 않는다.

## 시스템을 이해하는 데 필요한 큰 그림

학생과 개인 agent는 실제 업무와 원본 기록을 맡는다. 공용 시스템은 승인된 공유 근거를
편집해 Wiki(이해를 돕는 설명)와 dashboard(현재 변화·병목·다음 판단)를 만든다.
자기 공간에서 일한 결과가 공통 맥락으로 연결되므로 협업을 별도 할당량으로 만들지 않는다.
독립 목적·맥락·담당을 유지할 가치가 있는 업무를 프로젝트로 두며 연구/강의/행정은 태그다.
작은 일은 기타에 두고 필요할 때 독립시킨다. 주간 cadence가 main, 사건·응답 대응이 side다.
같은 일의 주간 목표와 응답 대기를 서로 다른 과업으로 복제하지 않는다.
월요일 미팅은 결과 마감보다 배운 점·방향·문제 해결·다음 집중점을 판단하는 주기다.

## 학생이 그대로 의뢰할 문장

> AGENTS.md와 WORKFLOW.md, 내 LOCAL.md와 현재 프로젝트 계획을 읽고 작업해줘.
> 실제 업무 결과와 실패를 기존 GitHub 기록에 축적하고, 미팅 합의와의 관계·남은 질문·
> 다음 시작점을 유지해줘. 공유·실행은 내 기존 위임 범위를 따르고 정리용 보고서를
> 중복 작성하지 마. 근거가 부족하면 이유와 최소 보완을 솔직하게 제안해줘.

첫 참여자는 원본 repository의 START-HERE.md에서 공간/계정 연결부터 시작한다.
기존 공간에 initializer를 재실행하지 않는다. 새 agent는 아래 순서로 현재 상황을 파악한다.

1. AGENTS.md → SYSTEM-PROTOCOL.md → 내 LOCAL.md/개인 위임 → current.md.
2. current가 연결한 프로젝트 최신 계획과 최근 실제 미팅 합의/본인 과업/정확 입력.
3. 명시 공유 범위와 도구/계정 상태. 공개 예제나 이 문서의 예시를 실제 승인으로 쓰지 않는다.

계획이 없으면 지금 할 일에 필요한 목표/역할만 확인한다. 모든 연구 연표·타인의 개인 원본은 읽지 않는다.
미팅 전 제안과 미팅에서 확정한 계획을 구분하고 구두 합의가 실제로 있었는지 추정하지 않는다.

Agent를 쓰지 않는 학생은 [직접 참여 체크리스트](https://github.com/nii-lab/niil-docs/blob/main/guides/student-without-agent.md)를 따른다.
같은 근거/미팅 준비 기준을 적용하고 agent의 문안 생성 여부로 준비를 구분하지 않는다.

## 1. 실제 작업과 함께 원본을 축적한다

코드·config·실험 출력·그림·독해 메모·실패를 이미 작업하는 위치에 보존한다.
대용량은 승인된 기존 저장소에 두고 GitHub에는 경로/버전/hash/접근 조건을 연결한다.
개인 기록은 담당 repository에 직접 commit/push, 공동 코드 변경은 fork/branch→PR을 따른다.
실행/commit/push는 수행·성공을 실제 확인한 단계만 보고한다. 실행하지 않은 수치/결과를 채우지 않는다.

기존 current/Issue/결과 설명에 아래 의미가 연결되면 충분하다. 매 파일에 양식을 복제하지 않는다.

| 의미 | 최소 기록 |
| --- | --- |
| 왜 했는가 | 합의한 질문/계획 링크와 이번 작업의 쓰임 |
| 무엇을 했는가 | 실제 입력/조건/변경·수행 주체(학생/agent/공동) |
| 무엇을 얻었는가 | 관찰·결과·실패와 정확한 파일/revision/근거 |
| 어떻게 해석하는가 | 확인된 사실/해석/한계·미확정의 구분 |
| 어디서 이어가는가 | 다음 시작점/필요한 판단/막힘과 필요한 도움 |

파일명·commit 수·성공 로그는 결과의 의미를 대신하지 않는다. Agent가 대행 실행한 결과도
유효한 작업이며 학생이 직접 수행/이해/검토했다는 뜻과 구분해 기록한다.
비공개 repo에도 다른 멤버의 Read 권한이 있을 수 있다. personal 표시는 파일 열람 차단이 아니다.
혼자만 볼 내용은 승인된 로컬 private 공간에 두며 개인 정책·비밀값·대화는 공유하지 않는다.

## 2. 정리는 시스템에 연결한다

source.uri는 GitHub의 OWNER/REPO/blob/<40자리commit>/PATH 고정 링크를 사용한다.
로컬 연습의 가상 URL은 운영 원본이 아니며 export 성공만으로 hub 호환/실제 게시를 증명하지 않는다.

단순 push만으로 중앙 Wiki가 갱신되지는 않는다. **현재 운영 집계 입력은 명시 공유된 Issue다.**
개인 agent가 결과를 근거로 최소 공유 기록을 만들고, 기존 위임 범위에서 같은 ID/Issue를
갱신한다. 새로운 중요한 결과/질문에만 새 기록을 만들고 무변화 댓글은 생략한다.
정리 작업은 agent가 맡으며 학생에게 같은 보고를 다시 쓰게 하지 않는다.

실제 전송 절차/명령과 인증·정책 부족 시 대응은
[연결 안내](https://github.com/nii-lab/niil-docs/blob/main/guides/connected-onboarding.md)를 따른다.
visibility=lab/status=accepted는 공유 확정이며 과학적 검증/Owner 수용이나 학생 확인을 뜻하지 않는다.

공용 편집은 [보고 기준](https://github.com/nii-lab/niil-docs/blob/main/guides/research-reporting.md)을 사용한다.
요약→맥락/전후 관계→판단에 적합한 그림·표→재현 근거로 깊이를 선택하게 한다.
원본/실패/이견을 보존하고 공유 source revision을 연결한다. 의미 없는 링크/중복 보고는 줄인다.

## 3. 미팅 준비는 공통 책임, 평소 수행은 자유

평소에는 실제 결과를 축적한다. 일일 시작/종료 체크나 별도 일지는 필수가 아니다.
미팅 전에 agent가 기존 근거에서 요약을 만들고 학생은 아래를 확인한다.

- 지난 합의에서 내가 맡은 일과 실제 시도/결과의 연결.
- 새로 알게 된 점·계획과 달라진 이유·실패/미진행/불확실성.
- 함께 논의할 질문과 다음 집중점 제안. 근거가 부족하면 그 이유와 필요한 보완.

미팅 준비 기록은 기존 공유 문서/Issue의 해당 주 구간을 재사용한다. 주차/담당 계획/근거/
학생 확인 상태/남은 질문이 연결되면 된다. 자동 초안은 학생 확인 전까지 prepared다.
학생이 실제 확인한 경우에만 확인 시각과 범위를 기록한다. Agent가 대신 확인했다고 쓰지 않는다.
학생 확인은 미팅 준비에 관한 것이며 기존에 위임한 통상 Issue 게시의 새 승인 조건은 아니다.

실패했어도 근거와 질문이 준비되면 미팅 준비는 충분할 수 있다. 연구 결과의 충분성은 별도다.
누가 무엇을 맡고 준비했는지 추적하되 미확인/접근 불가를 무기여로 단정하지 않는다.
미팅 후에는 실제 결정/미정·다음 담당과 점검 기준을 반영한다. 합의가 없으면 제안으로 유지한다.

## 4. 학생에게 솔직하고 구체적으로 코칭한다

합의한 질문에 답하기 부족하면 의견을 제시한다. 분량/활동량보다 현재 근거로 가능한 판단을 본다.
피드백은 **현재 근거 → 어려운 판단 → 최소 보완 → 보완 후 가능한 판단**으로 쓴다.

예시(가상): “실행 로그는 있지만 목표 오차와 사용 config가 연결되지 않아 정확도는 판단하기
어렵습니다. 기존 결과의 오차표와 config revision을 연결하면 방법을 유지할지 논의할 수 있습니다.”

자료에서 이미 찾을 수 있는 내용은 먼저 찾아 연결한다. 기존 출력으로 충분하면 재실험을 제안하지 않는다.
추가 실행이 필요하면 목적/입력/자원/완료 기준을 기존 범위와 대조하고 범위 안에서 진행한다.
목표가 모호하거나 기준이 부적절하면 계획 조정도 제안한다. Agent의 미검토/접근 불가를 학생 부족으로 돌리지 않는다.
학생은 이견/이유를 남길 수 있다. 코칭은 공유·미팅 참석을 차단하는 검열이나 새 승인 단계가 아니다.

## 5. Quest와 업적은 수행을 돕는다

- 필수 Weekly: 위의 미팅 준비. 실제 연구 성공과 별도로 준비 여부를 본다.
- Reminder: 미팅 합의 중 현재 집중점1–2개. 알림을 위해 새 과업을 만들지 않는다.
- 선택 습관: 결과와 설정 연결, 독해 적용점 한 줄, 다음 시작점 남기기 등 실제 작업에 맞는 소수.
- 업적: 미팅 준비3회 연속, 기록 습관 개선, 질문 구체화, 스스로 다음 단계 제안 같은 개인 성장.

연속 달성은 선택적 축하다. 휴가/미팅 취소는 해당 주를 건너뛰고 이전 업적을 지우지 않는다.
성장은 과거/최근 실제 사례로 설명하고 근거가 없으면 후보로 둔다. 배지는 성적/기여 순위가 아니다.
추가 승인 의식·공개 순위·협업 횟수 할당 없이 기존 확인/피드백을 활용한다.

## 6. Wiki·Dashboard 환류를 실제 단계별로 확인한다

공유 Issue → GitHub event 집계 → source-bound 편집/해석 → member dashboard 순서다.
학생 agent는 본인 Issue ID/version/source와 생성 Wiki의 반영 상태를 대조한다.
[현재 상태 진입](https://github.com/nii-lab/niil-docs/blob/main/guides/login-and-next-task.md)의
등록된 hub generated branch/포털 경로를 사용한다. 같은 내용의 재전송은 생략한다.
공유 원본이 바뀌었는데 이전 해석이면 stale로 구분하고 유지보수 담당자에게 정확한 source를 연결한다.
학생 권한으로 중앙 편집/배포를 대신하거나 개인 source 전체를 중앙으로 수집하지 않는다.

완료 보고는 다음을 따로 쓴다: 원본 축적(commit/push) / 공유(Issue/version) / 학생 확인 /
Wiki(생성 revision/source 반영) / dashboard(snapshot/deployment/실제 화면 확인 여부).
접근이 없으면 미확인, 실패하면 원인/담당/다음 행동을 남기고 독립 가능한 일을 계속한다.
로컬 fixture 성공은 실제 GitHub 인증/서버 반영/웹 배포 성공이 아니다.

[환경·연결 진단](https://github.com/nii-lab/niil-docs/blob/main/guides/readiness.md)이 필요한 경우에만 읽는다.
미완료/외부 대기는 대상·재확인 조건·가능한 다음 행동을 남긴다. 빈 inbox를 상위 목표 완료로 해석하지 않는다.
연구 범위가 실제 종료됐다면 현재 결론/대표 결과/한계/다음 목적 유무를 정리하고 종료 계산을 반복하지 않는다.
